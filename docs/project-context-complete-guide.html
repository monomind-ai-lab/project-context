Project Context

A collaborator returning after three weeks should not have to rebuild the project from stale chats. Plain Markdown in your repository, read by people and agents alike.

v0.7.0 Why · Install · Records · Operate · Reference github.com/monomind-ai-lab/project-context

Part 1 · Why

Four questions every returning collaborator asks.

Documentation explains what the code does — the code already does that. Project Context records what the code cannot say.

Q1

What is true now?

Active state, blockers, and the next action.

Q2

Which decisions constrain the work?

Accepted choices, with the rationale intact.

Q3

What has already been learned?

Verified lessons worth reusing rather than re-paying for.

Q4

Where is the evidence?

A pinned link to the commit, review, or record that proves it.

↻ Project Context does not copy your project into a second knowledge base. Primary artifacts stay exactly where they belong.

Part 2 · Install

Install with any AI agent.

Paste this. The agent reads the protocol and proposes a plan before it writes anything.

Install Project Context in the current repository or project folder using https://github.com/monomind-ai-lab/project-context. Read and follow `skills/project-context-init/SKILL.md`, starting with its required onboarding question. Show me the proposed plan and wait for my approval before making changes.

--dry-run
Inspect the exact changes first — nothing is written
--apply
Create only what the plan listed, and nothing else
--install-hooks
Wire the session hooks in. Opt-in, never assumed

Part 2 · Install

Two profiles, and the smaller one is the default.

Every record is read on every session. You pay for what you keep, so keep less.

ProfileWhat lands
coreNOW.md, DECISIONS.md, LEARNINGS.md, decisions/ — enough for most repositories
fullAdds tasks/, designs/, incidents/ — take it when the project already has that much going on
Both write the same managed block into both CLAUDE.md and AGENTS.md, creating whichever is missing — so no harness is left with rules it never reads.

Part 3 · Records

A small set of files, each with one job.

NOW.md

Current state & blockers · ≤ 400 words

DECISIONS.md

Constraints & rationale

LEARNINGS.md

Verified, reusable lessons

decisions/

Detail records, when one needs room

The test for a decision is not "was this hard". It is: would someone six months from now redo this badly without knowing? If no, leave it out.

Part 3 · Records

Six required keys, and nothing else.

Detail records carry frontmatter. Registries stay plain Markdown, as they always were.

A detail record

--- id: D-004 kind: decision status: accepted title: Serve thumbnails from the CDN created: 2026-09-03 asserted_by: person:ren ---

Status depends on the kind
KindStates
decision · learningproposed → accepted → superseded | rejected
questionopen → answered → superseded
taskproposed → active → done | dropped
A question is not an assertion and a task is not a claim. One vocabulary for all three was wrong twice over — it left a finished task with no terminal state.

Part 4 · Operate

Two checks, and one of them is unusual.

The doctor · read-only
  • no-delivery-path — context is intact but nothing loads it. A perfect record set no session reads is worth nothing.
  • pushed-file-modified — a file the owner owns was edited here.
  • Record shape, stale NOW.md, drifted evidence anchors.

Exits 1 on any error, so CI and a git hook both use the exit status without parsing anything.

The trigger gate

It detects that work landed since the records were last touched, and nags once per session. It does not decide what to write — only you know whether a choice constrained future work.

ack
An honest "reviewed, nothing to record", bound to the commit it evaluated

Part 4 · Operate

Optional: working alongside a Project Hub.

A repository with no Hub is a complete product. When an organisation runs one, two folders arrive that you do not author.

You author these
  • NOW.md · PLAN.md
  • DECISIONS.md · decisions/
  • LEARNINGS.md · QUESTIONS.md

Yours to write. The owner copies them upward when they want to look; nothing here ever reaches out to them.

The owner pushes these — read-only here
  • global/ · guardrails, workflows, shared records
  • blueprint/EPIC.md · the plan this project serves
  • blueprint/ARCHITECTURE.md · the shape it must keep

Stamped by hash. Editing one is an error, because your change would be silently overwritten at the next sync and the owner would never learn you disagreed.

Disagree with something pushed? Raise a question in your own records. It reaches the owner with the project context that explains it.

Part 5 · Reference

What the tool will not do to your repository.

  • Existing context files are preserved byte-for-byte. Records are never rewritten by tooling.
  • Both AGENTS.md and CLAUDE.md get the same block, and whichever is absent is created. Everything outside the markers survives — file mode and CRLF endings included.
  • Unknown or overlapping memory is reviewed and classified, not migrated.
  • Malformed blocks, unsafe symlinks, and non-UTF-8 instructions stop apply mode before any write.
  • Zero runtime dependencies. Nothing here reaches the network.
