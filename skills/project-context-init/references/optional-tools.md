# Optional tool setup

Last reviewed against the official repositories: 2026-08-26.

Project Context is authoritative tracked Markdown. GitNexus, Graphify, and
OpenWiki are optional derived systems with different purposes. Always detect
both global availability and repository configuration before proposing a
change. Ask independently only about unconfigured tools that fit the confirmed
repository type and observed need, then install or configure only after an
explicit answer.

## Repository-type filter

- **Code:** consider GitNexus when meaningful source code needs structural or
  impact analysis. Consider OpenWiki only for stable, complex projects with a
  real audience for derived navigation. Graphify becomes relevant when the
  useful corpus extends beyond code.
- **Documents:** consider Graphify for a substantial, interlinked corpus and
  OpenWiki only when collaborators need a maintained generated browse layer.
- **Research:** consider Graphify for cross-source, data, and evidence
  relationships. Defer OpenWiki until claims and structure are stable.
- **Writing:** suppress GitNexus and OpenWiki. Consider Graphify only for a
  large multi-file manuscript, story world, or similarly relational corpus.
- **Mixed:** scope GitNexus to a meaningful code subtree, consider Graphify
  across artifact types, and offer OpenWiki only for a clear navigation use.
- **General or uncertain:** do not offer an add-on until inspection identifies a
  concrete need.

A tool on `PATH` is available, not necessarily configured for the repository.
Offer project configuration rather than reinstallation when appropriate.

Once the user opts in to the disclosed tool and scope, the agent performs and
verifies the installation or repository configuration automatically. Do not
delegate routine commands to the user. Secure provider authentication or secret
entry may still require user action, and later side effects remain separately
authorized as described below.

## GitNexus

Purpose: structural code intelligence for symbols, relationships, impact, and
execution flows. Recommended when the repository contains meaningful source
code and agents need change-impact or call-path queries.

Detection signals:

- `gitnexus` on `PATH` and its version, if callable;
- `.gitnexus/gitnexus.json`, legacy `.gitnexus/meta.json`, or
  `.gitnexus/run.cjs`;
- GitNexus-owned managed blocks in root harness files;
- `.gitnexusrc`;
- a GitNexus MCP entry in project-scoped Codex configuration.

Prerequisites and footprint: Node.js 22+, a Git repository by default, native
Tree-sitter and LadybugDB components, a local gitignored `.gitnexus/` index,
and a user-level registry. Platform caveats are documented upstream.

Least-invasive current path:

```sh
npx gitnexus@latest analyze --skip-agents-md --skip-skills
```

The two documented skip flags preserve root harness instructions and avoid
installing GitNexus project skills. A global CLI is optional:

```sh
npm install -g gitnexus@latest
gitnexus analyze --skip-agents-md --skip-skills
```

Core indexing and MCP queries require no API key and process code locally.
Optional embeddings may use a downloaded local runtime or an OpenAI-compatible
endpoint. `gitnexus wiki` is a separate LLM feature and may persist provider
settings in the user-level GitNexus config. Never pass API keys on a command
line generated by this skill, inspect their values, or publish a wiki/gist
without separate approval.

Codex setup is a separate choice. Use either `npx gitnexus setup -c codex` or
the official Codex plugin route, not both, because upstream warns duplicate
hooks can result.

Official sources:

- https://github.com/abhigyanpatwari/GitNexus
- https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/README.md
- https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md

## Graphify

Purpose: build a persistent graph across supported code, documents, papers,
images, audio, and video so agents can navigate cross-file concepts and
relationships. Recommend it for mixed-media or documentation-heavy corpora;
keep it optional for a small code-only repository already served by GitNexus.

Detection signals:

- `graphify` on `PATH` and its version/help, if callable;
- `.codex/skills/graphify/SKILL.md` or `.agents/skills/graphify/SKILL.md`;
- a Graphify-owned section in `AGENTS.md` or `.codex/hooks.json`;
- `graphify-out/graph.json`, `graphify-out/.graphify_root`, or
  `graphify-out/.graphify_python`;
- `.graphifyignore`;
- Graphify commands in project harness files or automation.

Prerequisites and footprint: Python 3.10+; the official distribution is
`graphifyy` (double `y`) and its CLI is `graphify`. The base install includes
NetworkX, NumPy, RapidFuzz, and Tree-sitter grammars. PDF, Office, video, MCP,
database, SVG, and model-provider extras are opt-in; do not install `[all]` by
default. There is no official fixed disk/RAM figure.

Preferred CLI installation and project-scoped Codex skill setup:

```sh
uv tool install graphifyy
graphify install --project --platform codex
```

Supported CLI alternatives include `pipx install graphifyy` and
`pip install graphifyy`. For a generic Agent Skills target, use
`graphify install --project --platform agents`. Do not use bare
`graphify install` for Codex because its current default targets Claude Code.
The separate `graphify codex install --project` route edits `AGENTS.md` and
registers a Codex hook, so ask for specific authorization before running it.

Possible project-scoped footprint, only for a mode the user specifically
authorizes: `.codex/skills/graphify/` or `.agents/skills/graphify/`. A graph
build produces derived `graphify-out/` artifacts such as `graph.json`,
`GRAPH_REPORT.md`, and `graph.html`, plus caches or conversion sidecars. Do not
silently add ignore rules.

Code structural extraction can operate locally without an API key. Semantic
extraction for non-code artifacts may use the host agent or a configured
backend. A fully local code-only command is:

```sh
graphify extract . --code-only
```

Ollama is the documented fully local semantic backend. Other current headless
backends include Gemini, Kimi, Claude, OpenAI-compatible endpoints, DeepSeek,
Azure OpenAI, and Bedrock IAM. Configure provider secrets outside tracked files
and verify only that they are present. Do not claim the entire pipeline is
offline unless the selected mode has been verified end to end. Leave shared
HTTP MCP on loopback; if the user deliberately exposes it, follow upstream API
key guidance. For sensitive repositories, support explicit query-log disabling
with `GRAPHIFY_QUERY_LOG_DISABLE=1` because upstream documentation currently
contains contradictory logging-default claims.

Official source:

- https://github.com/Graphify-Labs/graphify
- https://github.com/Graphify-Labs/graphify/tree/v8

## OpenWiki

Purpose: generate and maintain explanatory repository documentation. It is
useful when a browsable derived wiki justifies inference and maintenance cost;
it is never current-state authority.

Detection signals:

- `openwiki` on `PATH`;
- `openwiki/index.md`, `.last-update.json`, `.claims/`, `.run.json`, or
  `INSTRUCTIONS.md`;
- `.openwikiignore`;
- OpenWiki-owned managed blocks in root harness files;
- a project Codex integration under `.agents/skills/openwiki` and
  `.codex/config.toml`;
- an OpenWiki CI workflow.

Prerequisites and footprint: Node.js 22+, generated `openwiki/`, and user-level
state under `${OPENWIKI_CONFIG_DIR:-~/.openwiki}`. Initial generation requires
model inference. The Codex integration can use the host agent's authenticated
model session without a separate OpenWiki provider credential:

```sh
npm install -g openwiki
openwiki integrations install codex --project .
```

Native provider mode supports several cloud providers and OpenAI-compatible
local servers. Credentials belong in environment variables, CI secrets, or
OpenWiki's protected user-level store. Never commit them. `.openwikiignore`
sets a source-read boundary but cannot prevent inference of an ignored topic
from permitted files. Telemetry is enabled by default upstream and can be
disabled with `OPENWIKI_TELEMETRY_DISABLED=1` or `DO_NOT_TRACK=1`.

`openwiki --init` replaces generated wiki material (while preserving documented
user-owned files such as `INSTRUCTIONS.md`) and consumes inference. Treat it as
a separately authorized generation step. Use `openwiki --update` for later
updates after configuration.

Official sources:

- https://github.com/langchain-ai/openwiki
- https://github.com/langchain-ai/openwiki/blob/main/DEVELOPMENT.md
- https://github.com/langchain-ai/openwiki/blob/main/examples/openwiki-update.yml
